5.1 · Харнесс: пропускной пункт между моделью и миром

🎯 С кодом (Python) · ✅ Интерактивный квиз · ⏱️ ~14 минут

🎯 Зачем это бизнесу

Агент с доступом к файлам и командам — это сотрудник с ключами от всего офиса. Уровни 0–4 научили его дисциплине: папка проекта, договоры задач, роли. Но дисциплина — это инструкции, а инструкции модель иногда нарушает. Харнесс (англ. harness — «упряжь») решает это физически: слой между моделью и миром, через который проходит каждое действие. Модель может попросить что угодно — харнесс решает, что реально случится.

Разница принципиальна: «не удаляй файлы» — просьба. «Команда rm не входит в белый список» — свойство системы. Первое нарушается в пятницу вечером, второе — никогда.

📚 Что изучаем

Четыре механики харнесса

МеханикаЧто делаетПочему работает
1. Песочница путейПеред любой записью/чтением путь разворачивается до абсолютного и проверяется: остался ли внутри рабочей папкиresolve() схлопывает все «..» и симлинки до проверки — обойти нельзя
2. Белый список командЗапускает только разрешённые исполняемые файлы (например: pytest, git, python)Всё остальное отсекается до запуска, а не после беды
3. Верификация при записиКаждый .py после записи проходит проверку синтаксиса и линт — по exit-кодам, не по словам моделиРешение «годно/не годно» принимает машина — тот же принцип, что постусловие из урока 2.2
4. Журнал траекторииКаждое действие агента записывается в лог (какой инструмент, какие аргументы, результат)Аудит и повтор: «покажи, как агент это сделал» — как след из урока 3.5

Песочница: три строчки, которые не обойти

def validate_path(self, rel_path):
    # resolve() разворачивает '../..' и символические ссылки
    target = (self.workspace / rel_path).resolve()
    if not target.is_relative_to(self.workspace):
        raise PermissionError(f"{rel_path} выходит за пределы")
    return target

# Попытка write_file("../../../etc/passwd") -> PermissionError

Ключевая идея: сравнивать надо после разворачивания пути, а не до. Проверка строки «нет ли в пути двоеточий» ломается десятком трюков; проверка результата resolve() — не ломается ничем.

Верификация — внутренняя, а не инструмент агента

Тонкость из практики: проверка кода не проходит через тот же канал, что команды агента. Линт после записи — это бухгалтерия харнесса, а не действие модели. Поэтому в журнале траектории она не появляется: агент не может «попросить» пропустить верификацию, перезапустить её или подделать результат — она происходит мимо него.

Страховка от «чинил-чинил — сломал»: откат

Типичный сценарий без отката: агент пишет файл, проверка падает, агент чинит — хуже, чинит снова — ещё хуже. После трёх попыток файл сломан сильнее, чем до начала. Расширение харнесса — снапшот до первой записи: если после N попыток проверка всё ещё красная, файл автоматически возвращается в исходное состояние, агент получает чистую ошибку «откатились к оригиналу — начните заново».

Правило простое: агент никогда не должен оставлять после себя состояние хуже исходного. Либо улучшил и проверка зелёная, либо откат. «Почти починил» — не существует.

🛠️ Как применить

📊 Бухгалтерия: агент собирает отчёт

Харнесс ограничивает его рабочей папкой отчёта: записать в соседнюю с клиентскими данными — физически нельзя. Запустить что-то кроме конвертера и линтера — нельзя. Журнал траектории — готовый ответ на вопрос аудитора «кто и когда менял цифру».

⚖️ Юриспруденция: агент готовит договор

Шаблоны — только чтение, черновики — только в папку сделки, внешние команды запрещены полностью. Модель галлюцинировала пункт — не страшно, это черновик в песочнице. Модель «захотела» что-то удалить — харнесс не пустит.

🛒 Закупки: агент ведёт реестр цен

Запись в реестр сопровождается верификацией формата (все колонки, валюта, дата). Файл с битой строкой просто не принимается — агент обязан исправить до записи, а не «исправлю потом».

✅ Чеклист принятия результата

  • У агента с доступом к файлам/командам есть слой-харнесс, а не только инструкции
  • Пути проверяются после resolve() — «..» и симлинки не спасают
  • Команды — по белому списку, всё прочее отсекается до запуска
  • Верификация результата идёт по exit-кодам и не является инструментом агента
  • Журнал траектории пишется на каждое действие — можно восстановить «как было»
  • После серии неудачных правок — автоматический откат к исходному состоянию

📝 Проверка понимания

Вопрос 1: Почему проверка пути делается ПОСЛЕ resolve(), а не по строке «нет ли .. в пути»?

A) Так принято в стандартах безопасности
B) Строку пути можно обмануть (симлинки, двойные развёртывания), а развёрнутый абсолютный путь сравнивается с границей надёжно
C) Это быстрее работает

Вопрос 2: Почему верификация кода не должна быть «ещё одним инструментом агента»?

A) Чтобы экономить токены на вызовы
B) Инструмент агент может попросить пропустить или подделать; внутренняя проверка происходит мимо модели и её решений
C) Чтобы лог траектории был короче

Вопрос 3: Зачем харнессу механизм отката файла к исходному состоянию?

A) Чтобы сэкономить место на диске
B) Серия неудачных «починок» оставляет файл хуже исходного; откат гарантирует: либо улучшение, либо ничего
C) Чтобы агент не скучал

🎯 Главное из урока

Инструкции модель нарушает, свойства системы — нет. Харнесс превращает просьбы в свойства: песочница путей, белый список команд, верификация по exit-кодам мимо воли агента, журнал каждого действия и откат после безуспешных чинок. Агент с харнессом может ошибаться — но не может навредить.
